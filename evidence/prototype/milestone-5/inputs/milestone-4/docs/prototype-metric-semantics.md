# Milestone 4 synthetic metric semantics

This document describes implemented functional experiments in `prototypes/aether-poc/`. They use the accepted invented v1 bundle. They do not establish deployed schema compatibility, real source acquisition, physical timing accuracy, overhead, durability or production design. All 250 metric requirements and 58 associations remain unchanged; untested requirements are still present.

The new `docs/prototype-metric-execution-status.json` records current function execution and independent comparisons. Original M1/M2 planning/execution fields and fixture oracles remain unchanged historical bytes. `px_runtime_acceptance_status=blocked_unagreed_budget`, readiness false and real verification not_run remain explicit. A functional match is not a whole-PX acceptance pass or measured budget result.

## Input and observation boundaries

The construction checker verifies the whole bundle first. `load_scenario_input` reads and rehashes the indexed input envelope through confined paths; `load_expected` separately reads the oracle only in verification. Runtime APIs receive typed envelopes with known record kinds/allowed fields, bounded records/clocks, explicit record identities and clock domains. Used counter, memory and endpoint-snapshot fields are decoded into strict types; irrelevant stage-specific records are explicitly not evaluated. This is a finite local fixture contract, not a general live telemetry schema.

The parser is independent of the validation tool's private construction parser. It consumes actual HTTP response bytes for endpoint scenarios and retains family name, original sample name, declared type, HELP, native labels/value, source references, producer/scope/unit provenance, virtual capture time/clock/uncertainty and optional unknown publisher/subject. A valid unknown family remains unmapped with unknown units/subject. Native sample/type metadata is not proof of physical ownership.

The finite grammar supports HELP/TYPE, counter/gauge values and cumulative histogram bucket/count/sum samples. Limits are 1 MiB text, 64 samples and 256 bytes per label value. Quoted labels exclude embedded commas, quotes, braces and escapes. Summaries, exemplars, timestamps and arbitrary comment extensions fail explicitly. Values are finite/nonnegative within this synthetic subset; negative gauges can exist in other real exporter grammars, which are not qualified here. Counter and histogram-count tokens must be decimal integers (optional `.0`) no greater than 2^53−1; checking the original token prevents fractional large values from rounding into an apparently exact count. Gauge/sum values are finite f64; exact source precision beyond that representation is not claimed.

TYPE controls interpretation. `vllm:iteration_tokens_total` remains a histogram. Histogram grouping retains original `_bucket`/`_count`/`_sum` sample names and validates each matching non-`le` label population, ordered boundaries, nondecreasing cumulative integer counts and +Inf=count. Conflicting/missing types, malformed lines, duplicate labels/series and invalid histograms are errors. Malformed fixture packaging still fails before a negative semantic test is considered. Expected TYPE_INVALID/HISTOGRAM_INCONSISTENT verdicts require actual corresponding runtime errors.

Seven native producers preserve their own boundaries: vLLM, SGLang, Dynamo, TGI, Triton, native TensorRT-LLM and its Triton backend. Triton's pinned-memory pool stays server_all_models. Backend GPU memory labels remain source-reported labels; no device association is inferred. Exported KV block counts are not cache-hit rate, and snapshots are not raw execution events.

## Calculation rules

The positive PX02 JSON contains 100 at zero and 150 at 10,000,000 virtual microseconds. Its `.prom` artifact contains only the first value. The rate scenario therefore declares synthetic_record_input, preserves both raw records and computes (150−100)/(10,000,000/1,000,000)=5 requests/second for the explicitly bound Triton source-success population. It does not fabricate a second endpoint read or token rate. Rates require matching source/family/population/labels/incarnation/unit and a positive interval in a comparable zero-uncertainty clock. Reset/decrease, changed incarnation, clock mismatch, unresolved population or imprecise large counts yield unknown with a reason.

PX04 counts are combined only with explicit unique, count-consistent logical-ID overlap and an explicitly selected frontend boundary. Raw counts remain ten and ten while selected count is ten. Missing overlap or mismatched population yields unknown combined count; model labels do not establish overlap. PX05 uses matching MiB units and positive, consistent used/total/free values; missing/invalid total cannot be inferred from used/free. One supplied replica count remains one result, not one per GPU. Memory occupancy is not cache-hit ratio. Token-rate/cache-hit requirements remain visible and unprototyped pending their required inputs.

Aggregate count/sum/buckets and separate success counts cannot recover exact joint goodput or variance. Runtime inputs contain no proof worlds. Independent oracle proof checking demonstrates identical count/sum/buckets with variances .0625 and zero, and equal marginal success/timing populations with goodputs .1 and zero requests/second. Those values are not emitted as runtime request observations. Exact threshold qualification absent the necessary bucket/event evidence is unavailable; no quantile estimator or hidden latency objective is invented.

## Privacy, policy and verification

Original native labels are available in bounded transient parsed structures. The report projection preserves safe label keys model_name/model/version/memory_type/le/fixture and redacts other label values with an explicit key list. Policy records retain only safe fixture labels; their sensitive-marker field is omitted from reports. A final JSON/error boundary removes the synthetic marker from any unexpected string. Parser errors never echo raw lines. Serialized runtime reports, stderr, comparison diagnostics and functional ledgers contain no marker. Original invented input/source archives retain their verified bytes as historical test material; they are not sanitized customer-output artifacts.

Policy actions are interpreted as data decisions; no command, source enabling, workload restart or escalation is executed. Denied source, disabled family and unknown identity remain distinct. Required-null limits/agreements block readiness. Latest gauges and capture times do not fill missing source update/persistence/query timestamps. Supplied queue admitted/rejected IDs are authored expectations for M6, not actual admissions performed by this engine.

`run-scenario` produces actual results without oracle comparisons. `verify-scenario` runs the same code first, then compares target/value/unit/state to independent expected data; errors are handled only by explicit negative assertions. Comparison mismatches exit nonzero. Oracle counterexamples, unknown matches and later-stage deferrals remain distinct. `verify-milestone --milestone 4` reports all original assertions and never changes accepted fixtures or budgets. Stable reports contain no ports, wall timestamps or random paths. Result SHA-256 uses compact sorted-key JSON of the sanitized actual report, without a trailing newline; artifact hashes use exact file bytes.

The Rust `record_metric_evidence` example authors the functional ledger from the recorded passing summary, verifies all original group/variant/assertion/oracle identities, attaches report/input hashes and refuses conflicting existing output. An identical rerun is safe. It indexes evidence; it is not a signed execution attestation or an evaluated runtime-budget checker.
